# Mandarin Assistant — Architecture

> `fr.berliat.hskwidget`, appId `fr.berliat.hskwidget`. KMP Compose Multiplatform.
> This doc describes principles, layering, and runtime flows — not a file inventory.

## 1. Big picture

```
androidApp / iosApp          <- thin shells (1 Activity / 1 ComposeView + widget + share targets)
        | depends on
crossPlatform/commonMain     <- all product logic: UI, ViewModels, Room, prefs, domain
        | uses (never owns threads for)
crossPlatform/androidMain|iosMain <- expect/actual: OCR, TTS, DB file copy, Anki, billing, widgets
        |
libraries: pinyin4kot, hsktextviews, googledrivebackup, AnkiDroidAPIHelper
```

Dependency rule: **common → platform via `expect`, never the reverse.** Platform shells register delegates into common (`HSKAppServices.registerAnkiDelegators/registerGoogleBackup`) and emit intents into common (`AppIntentBus`). Common never imports `android.*` / `UIKit`.

UI rule: **single Compose tree per process** (`AppView` → `AppNavHost`). Android has one `MainActivity`; iOS has one `ComposeUIViewController`. Widgets, share extension, and services are separate OS entry points that talk to common through intents + services, not by hosting Compose.

## 2. Staged startup (why DI looks the way it does)

Widgets and share extensions must boot without the full app (no billing, no Anki permission, minimal I/O). Hence the hand-rolled locator in `core/AppServices.kt` + `core/HSKAppServices.kt`:

- Services have `Priority`: `Widget < PartialApp < FullApp`, plus `dependsOn` edges.
- `init(upToLevel)` topologically levels pending services, inits each level concurrently, fails fast on misconfiguration (crash) vs factory failure (`Status.Failed`).
- `HSKAppServices` minimal set at `Widget`: `snackbar, resources, appPreferences, database(→appPreferences), widgetsPreferencesProvider`. `PartialApp` adds `ankiStore, wordListRepo`. `FullApp` adds `HSKSegmenter` (Jieba preload). Anki delegate + Drive backup are `registerNow`'d later by the platform shell.

Boot sequence (`ui/application/AppViewModel.kt`):

```
shell creates AppViewModel(NavigationManager)
  -> init(): HSKAppServices.init(PartialApp)
  -> status=Ready(Partial): readyUp() [isReady=true], then finishInitialization()
      -> HSKAppServices.init(FullApp)
      -> handleDbOperations() [cleanTemp + disk backup]
      -> if didUpdateApp(): handleAppUpdate() [prefs migration, staged DB update trigger]
      -> executePendingActions()
AppIntentBus intents arriving before isReady are queued via executeWhenReady{}
```

Consequence for E2E/tests: anything touching `HSKAppServices.database/appPreferences/ankiStore` before `Ready(Partial)` throws. The seam is `HSKAppServices` — fake it there, not in each ViewModel.

## 3. Navigation + intents (two buses, two truths)

- `ui/navigation/NavigationManager.kt` is a singleton event bus: `navigate(Screen)` emits on `navigationEvents: SharedFlow(replay=1)`; `currentScreen: StateFlow` + `stackScreen: ArrayDeque` (cap 20) are analytics/backstack mirrors.
- `ui/navigation/AppNavHost.kt` owns the real backstack (`NavController`, start = `Screen.Dictionary`). It collects `navigationEvents` and forwards to `navController.navigate(route)`. Each `composable<Screen.*>` calls `registerScreenVisit()` to mirror state back into `NavigationManager`.
- `ui/navigation/Screen.kt` is the route contract: `Dictionary(search?)`, `Lists`, `Annotate(word)`, `Widgets(id?, expectsActivityResult)`, `Config`, `About`, `Support`, `OCRCapture`, `OCRDisplay`. Navigation between features is always via these types (e.g. Lists→Dictionary with `SearchQuery(inListName)`, Dictionary→Annotate, Capture→Display→Annotate).
- `ui/application/AppIntent.kt + AppIntentBus.kt` is the *external* bus: deep-links, share sheet, widget taps, TTS (`Search, SearchTTS, WidgetConfiguration, ImageOCR, OCRCapture`). `AppViewModel.handleAppIntent` translates them into `Screen` navigations. This is what `hskwidget://search?q=` (iOS) and `PROCESS_TEXT/SEND` (Android) emit into.

Mental model: **OS → AppIntent → Screen → NavController**. Tests should inject at the `AppIntent` or `Screen` level, not by tapping through drawers.

## 4. Data: immutable dictionary + user overlay

Central read model is `AnnotatedChineseWord` = `ChineseWord? + ChineseWordAnnotation?`:

- `chinese_word` (+ `word_definition` per-locale, FK CASCADE) is **read-only asset data**, regenerated by `database_generation/` (CC-CEDICT/CFDICT/HSK/BCC/AI fields) and shipped as `Mandarin_Assistant.db`.
- `chinese_word_annotation` (+ `word_list/entry`, `widget_list_entry`, `chinese_word_frequency`) is **user data**. All writes go here.
- Reads (`data/dao/AnnotatedChineseWordDAO.kt`): `annotation LEFT JOIN word UNION word LEFT JOIN annotation`, over three FTS5 tables (`chinese_word_fts`, `word_definition_fts`, `chinese_word_annotation_fts`, `unicode61`) with a `LIKE` fallback (`searchFromStrLikeSimpleRows`) and a hand-weighted `order_by_logic` (exact > prefix > contains, then `popularity`, then recency). `hydrate()` fills per-`Locale` definitions afterwards.
- Writes: local-first. `AnnotateViewModel` → `ChineseWordAnnotationDAO.insertOrUpdate` + `WordListRepository` updates system lists (`Annotated`, `Exam`). Anki is **deferred**: repo mutators return `suspend () -> Result<Unit>?` Anki lambdas executed later by `HSKAnkiDelegate` on a Fragment/Activity thread (permission-gated). Never assume DB write ⇒ Anki write in the same transaction.
- Prefs (`data/store/PrefixedPreferencesStore.kt`): one DataStore file, key namespacing by `prefix` (`""` = `AppPreferencesStore`, `"widget_$id"` = `WidgetPreferencesStore`). `PreferenceState` is a two-way `StateFlow` bound directly to Compose — the search query itself (`AppPreferencesStore.searchQuery: SearchQuery`) is persisted state, which is why `AppNavHost` syncs `Screen.Dictionary(search)` into it.

## 5. DB lifecycle: blue-green, never in place

`domain/DatabaseHelper.kt` — live DB is never overwritten:

```
boot: recoverPendingUpdate() [journal STAGED|SWAPPED] -> if first launch: copy asset -> live
      elif shouldUpdateDatabaseFromAsset(appVersion in {32,37,48,64}): performStagedUpdate()
performStagedUpdate: VACUUM INTO live->.bak | copy asset->.new | replaceUserDataInDB(.bak->.new)
                     | verify counts (.new vs expected) | journal STAGED -> atomicMove(.new->live) -> verify -> clear journal
```

`replaceUserDataInDB` runs in one `immediateTransaction`: copies annotations, remaps list IDs (system lists matched by name), drops list entries pointing at words absent from the new dictionary, carries Anki deck IDs + frequencies + widget links. `postReplaceUserDataInDB` rebuilds derived system lists. Crash windows are covered by `.bak` + journal; `.new` without journal is discarded. `MIGRATION_1_2/2_3` only cover user-table shape; dictionary content comes from the asset, not migrations.

## 6. Widgets, OCR, sync: shared logic, native shell

- Widgets: `CommonWidgetController` (pick `getRandomWordFromLists(allowedIds, excludeCurrent)`, persist `widgetStore.currentWord`) + `expect WidgetController.redrawWidget` (Android = RemoteViews via `FlashcardWidgetProvider.android.kt`, iOS = `WidgetCenter.reload` via `WidgetPlatformDelegate`). Config is just `Screen.Widgets`; a `DummyWorker` suppresses spurious `APPWIDGET_UPDATE`s on Android.
- OCR: `expect HSKOCR` (Android = MLKit Chinese, iOS = Vision `VNRecognizeTextRequest` zh-Hans/Hant) → `CaptureImageScreen → OCRDisplay → Annotate`. Segmentation via `hsktextviews` + Jieba (`JiebaHSKTextSegmenter`, `FullApp` priority, preloaded off-thread).
- Anki: `expect AnkiDAO` (Android = AnkiDroid `ContentResolver`, iOS = stub) + `AnkiStore` (model/cards) + `WordListRepository` (local+deferred) + foreground `AnkiSyncWordListsService` on Android / empty actual on iOS.
- Backup: `DatabaseBackupDisk` (FileKit bookmarks) on every boot if enabled; `GoogleBackupService` (Android = foreground upload/download services, iOS = in-process coroutine) over the `googledrivebackup` module.
